# 엔지니어링

[← 저장소로](../README.md) · [구조](architecture.md) · [디자인 과정](design-process.md) · [결정 기록](decisions.md) · [일정표 끌기 수정 기록](postmortem-timetable-drag.md)

같은 제품을 Swift와 TypeScript로 두 번 만들면서, 두 앱이 어긋나지 않게 하려고 만든 검사들을 정리했다. 공유 시험 사례, 화면 스냅숏과 크기 훑기(끌기 측정 포함), 번역 검사, 대비 검사, 성능 측정, 화면과 말 점검, 일하는 방법 순서다.

## 1. 공유 시험 사례

두 앱은 코드를 나누지 않는다. 대신 기능마다 사례 표를 먼저 쓰고, 두 앱이 표의 모든 줄을 같은 기대 문자열로 통과하게 했다. 개발하는 동안 표는 `intent-cases.md`, `ribbon-cases.md` 같은 문서였다. 공개 저장소에는 그 문서가 없고, 표를 옮겨 적은 두 시험 파일이 기준이다. 할 일 스페이스(1.45/1.30)부터는 표를 JSON 파일 하나(`docs/plans/spaces-cases.json`)로 두고 두 앱의 시험이 그 파일을 같이 읽는다.

입력 줄 사례 1번은 두 앱에서 이렇게 생겼다.

```swift
// mac/Tests/PaperCoreTests/IntentTests.swift
(1, .ko, "내일 3시 회의", [:], ["event \"회의\" 2026-10-09 15:00–16:00 ⟨일정 · 내일(금) 15:00–16:00⟩",
                              "todo \"회의\" reminder 2026-10-09 15:00 ⟨할 일 · 알림 내일 15:00⟩"], "-"),
```

```ts
// windows/test/intent.test.ts
[1, "ko", "내일 3시 회의", {}, "event \"회의\" 2026-10-09 15:00–16:00 ⟨일정 · 내일(금) 15:00–16:00⟩; todo \"회의\" reminder 2026-10-09 15:00 ⟨할 일 · 알림 내일 15:00⟩", "-"],
```

뜻 후보의 순서와 날짜, 칩에 보일 글(⟨…⟩)까지 한 줄에 들어 있어서, 한쪽 구현만 바꾸면 그쪽 시험이 바로 깨진다.

입력 줄 사례만 136줄이다. 표를 먼저 쓰니 "Windows에서는 다르게 읽힌다" 같은 차이가 구현 전에 드러났다. 한쪽에서 버그를 찾으면 표에 한 줄을 더하고, 그 줄이 다른 쪽에서도 실패하는지 본다.

스페이스 사례 파일은 Mac이 먼저 쓰고 Windows가 같은 파일을 읽어 돌렸다. Mac 쪽 사례까지 45개, Windows도 S1–S22를 한 사례씩 통과한다. 파일 하나라서 한쪽만 고치는 일이 없다.

약점도 있다. 사례 일부(시간 범위, 검색)는 내 시간대 Asia/Seoul을 전제로 쓰였다. 그래서 CI는 두 워크플로 모두 `TZ=Asia/Seoul`로 돌린다. 달력 사례는 처음부터 시간대와 무관하게 써서 로스앤젤레스와 채텀 시간대에서도 통과한다.

## 2. 스냅숏과 크기 훑기

UI 시험은 버튼이 있는지보다 그려진 화면을 본다.

macOS에서는 `mac/scripts/render-design.sh`가 실제 SwiftUI 뷰에 예시 데이터를 넣어 PNG로 저장한다(`Tests/PaperTodoTests/DesignSnapshots.swift`). 한국어, 영어, 네덜란드어와 낮/밤을 모두 그리면 약 2,100장이다(메모 서랍의 네 종이, 메뉴, 바탕, 스페이스 포함). 다시 그린 그림은 시계와 날짜, 고양이 걸음만 다른 것을 빼고 따로 커밋한다. 글자를 읽어(OCR) 날짜와 시각을 지운 뒤 비교하고, 바뀐 픽셀 수를 함께 본다. 사용자 목록이나 설정은 읽지도 쓰지도 않는다. `scripts/test-presentation.sh`(47개)는 화면 상태, 키보드, 공유 폴더, 메모 합치기, 백업, 책상, 종이 색, 집중, 실제 창으로 연 쪽지의 크기(1.42.1)를 확인하고, 손글씨 제목의 마지막 글자가 잘리는지 픽셀로 본다('Ahead', 'coffee', '커피 coffee'). 시험용 앱은 다른 번들 ID와 저장 폴더를 쓰고, 알림은 화면 밖(`PAPERTODO_OFFSCREEN=1`)에 그린다.

Windows에서는 `npm run snapshot`이 모든 창을 화면 밖에서 그리고 크기 훑기(size sweep)를 돌린다.

- 창마다 가장 작은 크기부터 2560 × 1440까지, 배율 125%와 150%, 다른 글꼴(Noto, 붓, 깔끔), 밤 종이로 그린다.
- 크기마다 페이지 안의 검사(`src/main/layoutCheck.ts`)가 옆으로 스크롤되는 상자, 말줄임 없이 잘린 글, 아래가 잘린 글, 창 밖으로 나간 요소, 이웃과 겹친 요소, 상자 밖에서 잘린 손글씨 잉크, 보이지 않는 입력 칸 안내 글을 찾는다. 하나라도 있으면 실패하고, 없으면 `SWEEP OK`를 출력한다.
- 말줄임은 실패로 치지 않고 따로 적어 둔다. 좁은 창에서는 괜찮지만, 넓은 창에서 말줄임이 보이면 자리를 못 쓰고 있다는 뜻이라서다.

잉크 잘림 검사는 처음부터 있던 게 아니다. Caveat와 Kalam의 d, e, f, k 끝이 칸 밖으로 나가 'Ahead'가 'Aheaa'로, 'coffee'가 'coffe'로 보였고, 이걸 Windows 1.22.1과 Mac 1.37.1에서 고치면서 검사를 더했다.

두 플랫폼의 스냅숏이 같은 화면 이름으로 나오니, Mac과 Windows 그림을 나란히 놓고 다른 곳을 찾을 수 있었다. 새 디자인 네 단계를 마친 뒤의 점검 판(Mac 1.37.1, Windows 1.22.1)이 그렇게 나왔다.

### 끌기를 틱마다 재기 (Mac 1.41, Windows 1.26)

멈춘 화면은 움직이는 동안의 문제를 보여 주지 못한다. 하루 일정표 블록이 끄는 동안 떨리던 문제(Mac 1.40)는 스냅숏 약 1,500장과 시험을 모두 통과한 상태에서 내가 쓰다가 찾았다. 그래서 끄는 동안 블록이 그려진 위치를 틱마다 기록하는 도구를 두 앱에 하나씩 만들었다.

- macOS `scripts/drag-check.sh`: 다른 번들 ID의 디버그 사본을 만들어 할 일 하나를 넣고 띄운다. 사본에 보낸 가짜 마우스 이벤트는 SwiftUI `DragGesture`까지 가지 않아서, 디버그 빌드에만 있는 재생 장치(`--timetable-replay`, `TimetableReplay.swift`)가 제스처와 같은 함수를 초당 60번 부르며 옮기기, 아래 끝, 위 끝, `Esc`, 일정표 아래로 넘기기를 재생한다. `drag-check.py`가 틱마다 블록과 포인터의 차이, 반대로 튄 횟수, 다른 블록을 다시 그린 횟수를 판정한다. 설치된 앱과 데이터는 건드리지 않는다.
- Windows `tools/drag-probe.mjs`: `--demo`로 띄운 앱에 CDP로 실제 마우스 이벤트를 1px씩 보내고, `requestAnimationFrame`마다 끌리는 블록의 `top`을 기록한다.
- `scripts/drag-sim-1.40.py`는 옛 계산을 같은 포인터 경로로 재현한다. 118틱 동안 블록 위치가 114번 바뀌고 61번은 포인터와 반대 방향이었다.

| | 고치기 전 | 고친 뒤 |
| --- | --- | --- |
| Mac 옮기기, 포인터와 최대 차이 | 51.5pt (두 칸 사이를 오감) | 0.20pt (118틱, 반대로 튐 0) |
| Mac 위 · 아래 끝 늘리기 | — | 0.00pt (30틱, 60틱) |
| Windows 옮기기 | 최대 6px, 216프레임 중 1px 안 38프레임 | 0px (225프레임) |
| Windows 위 · 아래 끝 | — | 0px (75프레임, 180프레임) |
| 끄는 동안 다시 그린 것 | Mac은 한 칸마다 일정표 전체 | 시작할 때 일정표 한 번, 끌리는 블록만 |

원인과 고친 방법은 [수정 기록](postmortem-timetable-drag.md)에 있다.

## 3. 번역 검사

한국어 원문이 키다. 한국어로 문구를 쓰고 영어와 네덜란드어 표를 채운다. 영어와 네덜란드어 문구는 AI가 초안을 썼고, 아직 원어민 검토를 받지 않았다. 아래 검사는 빠진 번역과 형식 오류를 막을 뿐 문장이 자연스러운지는 보지 못한다.

- macOS의 `scripts/i18n/check.sh`는 컴파일러가 뽑은 모든 문구에 영어와 네덜란드어가 있는지, 자리표시자가 맞는지, 번역을 거치지 않은 한글 문구가 코드에 남았는지 검사한다. `scripts/test-localization.sh`는 세 언어로 앱 문구와 손글씨 글꼴(라틴 글자는 Caveat와 Kalam, 한글은 한국어 손글씨)을 확인한다.
- Windows의 `test/i18nStrings.test.ts`는 `src/main`, `src/renderer`, preload에서 `t()` 밖에 남은 한글과 영어/네덜란드어에 없는 키를 찾아 실패시킨다. 복수형은 `{n|one|many}`로 쓴다.
- 날짜, 시간, 입력 줄, 종이냥 한마디처럼 코어가 만드는 말은 두 앱이 같은 사례로 검사한다. Windows `i18n.test.ts`와 같은 사례를 Mac `CoreTests`가 돌린다.

## 4. 대비 검사

색은 모두 이름 붙은 토큰(종이, 먹 세 단계, 줄, 세이지, 점토, 탭, 테이프)이고 낮과 밤 두 벌이 있다. 두 앱의 최종 색표는 같다.

- macOS `scripts/check-contrast.py`는 낮과 밤의 글자/바탕 111쌍과 메모 서랍 네 종이(낮, 밤, 크라프트, 모눈)의 234쌍을 표로 출력하고, 하나라도 WCAG AA(본문 4.5:1, 큰 글씨와 UI 3:1)에 못 미치면 실패한다. 1.45부터 `scripts/test-contrast.sh`가 다른 시험과 함께 이 표를 돌리고, 모든 색 토큰이 표에 있는지, Windows 앱과 같은 값인지(공유 토큰 43개)도 본다.
- 스페이스 띠 8색은 낮 · 밤 종이와 카드 위에서 3:1 이상(가장 낮은 낮 3.31, 밤 4.58), 띠 · 칩 · 머리말 버튼 위 글자는 4.5:1 이상이다.
- Windows `test/contrast.test.ts`, `test/drawerContrast.test.ts`는 같은 표를 같은 기준으로 검사한다.
- 쪽지와 서랍 종이의 차이처럼 장식이라 기준이 없는 쌍은 숫자만 출력한다. 기준을 넘어도 잘 안 읽힌 일(밤 종이 서랍, 1.43.1)이 있어서다. [문제 해결 기록 6번](../portfolio/troubleshooting.md#6-밤-종이-서랍의-글자가-눈에-안-들어옴-mac-1430--1431-windows-1280--1281)

## 5. 성능

같은 도구와 같은 데이터로 고치기 전과 후를 쟀다.

- 데이터: 할 일 150개, 일정 60개, 완료 기록 2,000줄, 메모 80개의 시험용 목록(`mac/scripts/perf-data.py`, `windows/tools/perf-data.mjs`).
- macOS `scripts/perf.sh`: 다른 번들 ID로 시험용 사본을 만들어 그 프로세스만 조작하며 CPU, 메모리, 반응 시간을 잰다. 설치된 앱과 데이터는 건드리지 않고, 끝나면 사본이 쓴 파일을 지운다.
- Windows `npm run perf`: `--demo`로 띄운 앱을 DevTools 프로토콜(렌더러)과 Node 인스펙터(main)로 잰다. 시작 시간, 쉬는 동안 CPU(`app.getAppMetrics`), 메모리, 입력과 탭 전환 지연, 쉬는 동안의 파일 읽기를 본다.

### macOS 1.38 → 1.39

| 항목 | 1.38 | 1.39 |
| --- | --- | --- |
| 노트를 열어 두고 쉴 때 CPU | 61% | 0.7% |
| 노트가 가려지거나 닫혀 있을 때 CPU | 87% | 0.3% |
| 입력 줄 글자 하나 | 0.46초 | 0.01초 |
| 탭 바꾸기 | 몇 초 (밀림) | 0.13초 |
| 검색 열기 | 2.0초 | 0.2초 |
| 켜서 노트가 보일 때까지 | 2.7초 | 1.0초 |
| 10분 쓴 뒤 메모리 | 213MB | 136MB |

가장 큰 원인은 하루 띠였다. 1.34에서 들어간 '지금' 선은 숨 쉬듯 깜빡였는데, 깜빡이는 동안 노트 전체가 매 프레임 다시 그려지고 있었다. 노트를 열어 두면 CPU를 45–85% 썼고, 가려져 있으면 더 썼다. 성능을 재 보기 전까지는 몰랐다. 1.39에서 깜빡임을 Core Animation에 넘겼고, 1.40에서 띠를 새로 그리면서 '지금' 눈금은 아예 깜빡이지 않게 했다. 지금은 분이 바뀔 때와 내용이 바뀔 때만 다시 그린다.

나머지 원인은 이랬다.
- 노트 창이 크기를 정하려고 목록 전체를 매번 다시 쟀다.
- 입력 줄이 글자를 칠 때마다 같은 규칙을 수십 번 새로 만들었다. 이제 한 번 만들고, 같은 글에는 앞의 결과를 다시 쓴다.
- 완료 기록 2,000줄을 읽으면서 날짜마다 날짜 읽는 도구를 두 개씩 새로 만들었다. 검색, 기록, 책상을 처음 열 때 1초 넘게 멈춘 이유다.
- 목록이 화면 밖의 줄까지 만들었고, 탭 줄은 도구 단추를 매번 다시 그렸다.

Windows에도 같은 종류의 문제가 있었다. 하루 띠의 '지금' 점이 매 프레임 그려졌고, 숨긴 펫 창에서도 숨쉬기 애니메이션이 돌았다. 알람이 울린 뒤에는 숨겨 둔 쪽지의 물결이 계속 움직였다. 앱 상태를 모든 창에 보냈고, 바뀌지 않은 줄과 띠와 탭을 다시 그렸고, 공유 폴더를 확인할 때마다 파일을 통째로 읽었다. 지금은 파일 크기와 수정 시각을 먼저 보고 바뀐 것만 읽는다. 펫이 나와 있을 때의 CPU(약 4–7%)는 줄이지 못했다.

> 숫자는 모두 내 Mac 한 대에서 잰 값이고, 그날 컴퓨터가 얼마나 바빴는지에 따라 조금씩 달라진다. Windows 빌드의 숫자도 macOS 위 Electron에서 쟀다. 실제 Windows PC에서 잰 숫자는 없다.

### 메모 서랍과 AI 연결 (Mac 1.42–1.44, Windows 1.27–1.29)

새 창이 늘어도 쉴 때 CPU가 오르지 않게 했다. 서랍은 처음 열 때 만들고 그다음부터는 숨겼다 보여 주며, 닫혀 있는 동안 메모가 바뀌어도 다시 그리지 않고 열 때 바뀐 것만 반영한다. 손잡이는 바뀔 때만 그린다.

| 항목 | 값 |
| --- | --- |
| Mac 서랍 처음 열기 / 다시 열기 (1.43) | 0.11–0.13초 / 0.03초, 메모 200장도 같음 |
| Mac 서랍을 열어 두고 쉴 때 (1.44) | 불투명 0.41–0.50%, 반투명 0.41–0.46% |
| Windows 서랍 처음 열기 (1.28.1 → 1.29) | 186ms → 137ms |
| Windows 서랍 다시 열기 | 17ms → 3ms (닫혀 있는 동안 바뀐 게 없으면 다시 그리지 않음) |
| Windows 서랍을 열어 두고 쉴 때 | 0.91% → 0.22% |

Mac 1.44에서 카드에 머리말, 종류 표시, 테이프가 늘어 서랍 열기가 조금 느려졌다(처음 87–94ms → 96–99ms, 다시 19–22ms → 23–26ms). 카드 글 분석은 글이 바뀔 때만 하고 그림자를 단순한 사각형에만 그려서 이 정도로 줄였다.

### 메모가 많고 길 때 (Mac 1.45, Windows 1.30)

메모 2,000장, 5,000장, 1MB 메모를 넣고 서랍을 따로 쟀다(`mac/scripts/perf-memo.sh`, `perf-compose.sh`, `bench-memo-stress.sh`, `windows/tools/perf-memo.mjs`). 먼저 재기만 한 보고서를 쓰고, 고친 뒤 이전 서랍과 번갈아 다시 쟀다. 기록은 [`docs/perf-memo-stress.md`](perf-memo-stress.md)에 있다. 다른 빌드로 바쁜 Mac이라 숫자 하나는 30%쯤 흔들린다.

| 항목 (Mac, 한 키) | 고치기 전 | 고친 뒤 |
| --- | --- | --- |
| 짧은 메모에 한 글자, 50장 | 41–60ms | 8ms |
| 같음, 2,000장 | 694ms | 9ms |
| 같음, 5,000장 | 0.9–1.7초 | 8ms |
| 1MB 메모에 한 글자 | 0.7–0.8초 | 16ms |
| 한글 조합 중 한 타, 50장 / 2,000장 | 40ms / 286ms | 3ms / 4ms |
| 조합하는 동안 메모 목록이 바뀐 횟수 | 74번 | 0번 |
| 서랍 다시 열기, 2,000장 | 0.17–0.26초 | 51–60ms |
| ↓로 한 칸, 5,000장 | 1.5–2.6초 | 39–42ms |
| `memo-folders.json` 읽기, 2,000장 | 807ms | 5ms |
| 찾는 게 없는 검색, 2,000장 | 394ms | 44ms (다음 글자 2–3ms) |

- 원인은 한 글자마다 모델이 네 번 바뀌고, 그때마다 목록 전체를 다시 계산하고 모든 창이 다시 그려지던 것이었다. 한글을 조합하는 동안에는 낱자 하나하나가 그렇게 흘러갔다.
- 이제 서랍이 펼친 메모의 키를 갖고 있다가 마지막 키 0.25초 뒤에 한 번 모델에 넘긴다(닫기, 다른 메모, 지우기, 백업, 끄기에는 바로). 조합 중인 글자는 글 상자 밖으로 나가지 않는다. 목록은 메모 · 폴더 · 정렬이 바뀔 때만 한 번 만들고, 폴더 파일의 날짜는 형식기 없이 읽고 저장은 뒤에서 한다. 검색은 마지막 키 0.08초 뒤에 찾고, 메모의 줄은 한 번 읽어 둔다. 결과와 순서는 옛 방식과 무작위로 비교하는 시험으로 지켰다.
- Windows는 펼친 메모에 한 글자 칠 때 서랍 전체를 다시 재지 않고 글이 칸을 넘칠 때만 키운다. 2,000장에서 한 글자 94ms → 11ms, 5,000장 245ms → 40ms. 고친 글은 손이 0.15초 멈추면(쉬지 않고 쳐도 1초마다) 보낸다.
- 남은 것: Mac 서랍을 처음 열 때 2,000장에서 0.17–0.2초, Windows 5,000장에서 한 글자 40ms와 1MB 메모의 0.2–0.4초. Windows는 보이는 카드만 그리는 일이 다음 차례다.

### 할 일 2,000개에서 입력 줄이 몇 초 멈춤 (Mac 1.45)

스페이스의 성능을 재다가 찾았다. 오늘 탭에 할 일이 1,900줄쯤이면 빈 입력 줄에 첫 글자를 칠 때와 `Esc`로 비울 때 노트가 몇 초씩 멈췄다. 1.44에도 있던 일이다.

| UI/UX 점검 1 | 노트, 책상의 모든 칸, 쪽지, 메뉴를 두 앱의 스냅숏(ko · en · nl, 낮 · 밤, 2배)과 코드로 | 이슈 19개. 쪽지 테이프, 기본 버튼의 ↩ 표시, 할 일 메뉴의 순서와 아이콘, ⋯ 메뉴 묶음, 책상 칸의 행 모양, nl 잘림 |
| 문구 점검 | 두 앱의 모든 화면 글과 번역, 종이냥 한마디, 사이트, README | 이슈 9개와 [글쓰기 가이드](writing.md). 저장 오류, 확인 쪽지, 빈 상태, AI 연결 안내, 처음 안내 |
| UI/UX 점검 2 | 점검 1과 스페이스, 메모 서랍 새 모습, 말 다듬기가 들어간 뒤의 두 앱 | 이슈 9개와 사용자가 고를 것 넷. 이번 판 전에 고칠 것(P1): 타이머 남은 시간이 시각처럼 읽힘, ‘다음’ 줄에 붙은 표시, Windows 서랍 버튼이 날짜를 가림. 같은 판에서 nl 남은 시간과 고른 것(줄 위 버튼 셋, 책상 목록 아이콘, 입력 줄 키, 책갈피 이름)도 넣었다 |

- 점검 문서는 계획만 쓰고 코드는 바꾸지 않는다. 문제마다 그림 이름, 왜 문제인지, 제안, 크기와 위험을 적고 이슈로 나눈다.
- 사용자가 골라야 하는 것(단색 탭, 서랍 글자 시안, 줄 위 버튼 수)은 시안을 먼저 만들어 고르게 했다.
- 고친 뒤에는 스냅숏을 다시 그려 2배로 잘림을 본다. 낱말은 [용어표](terms.md), 문장은 [글쓰기 가이드](writing.md)를 따른다([ADR 10](decisions.md#adr-10-화면의-말은-글쓰기-가이드-하나를-따른다)).

# macOS (Swift 6, macOS 14 이상)

# Windows (Node 22 이상)

npm test                          # 582

GitHub Actions 워크플로는 두 개다. `.github/workflows/ci.yml`(README 배지)은 Windows 앱의 타입 검사와 시험을 macOS 러너에서 돌린다. `.github/workflows/mac.yml`은 Xcode 26 러너에서 Mac 앱을 빌드하고 코어 시험, 대비 검사, 번역 검사를 돌린다. Xcode 26 이미지가 없으면 이 워크플로만 실패하도록 둘을 나눴다.

## 8. 일하는 방법

혼자 만들지만 팀처럼 일한다.

- 문제는 고치기 전에 이슈로 먼저 올린다. 한 이슈에 문제 하나, 버그는 무엇 · 다시 일으키는 법 · 기대와 실제 · 환경 · 끝난 기준. 실제 Windows PC에서 확인이 필요하면 `verify` 라벨을 단다.
- main은 언제든 릴리스할 수 있는 상태다. 일은 짧은 브랜치(`feat/…`, `fix/…`, `design/…`, `copy/…`, `perf/…`)에서 하고, 혼자여도 PR로 머지 커밋을 남긴다. PR 본문은 무엇을 · 왜 · 확인한 것 · `Fixes #N`.
- 커밋은 Conventional Commits에 범위를 붙인다: `fix(win-popup): …`, `perf(mac-drawer): …`. 다시 그린 스냅숏은 `chore(snapshots): …`로 따로 커밋해 코드 변경을 읽기 쉽게 한다.
- 머지 전에 두 앱의 빌드, 시험, 번역 검사, 대비 검사를 돌리고, 화면이 바뀌면 스냅숏을 2배로 본다. 예시는 지어낸 것만 쓰고 로컬 경로를 남기지 않는다.
- 릴리스 노트는 정해 둔 목차(요약 · 새 기능 · 개선 · 고친 문제 · 업데이트 전에 · 알려진 문제 · 내려받기)로 파일에 먼저 쓰고 다듬는다.

## 아직 못 한 것

- Windows 앱은 macOS 위의 Electron에서 모든 화면과 동작을 확인하고 설치 파일을 만들었다. 실제 Windows PC에서는 한 번도 돌려 보지 않았다. 설치 과정, 알림 영역, 클릭 통과(할 일 알림의 체크), `Ctrl+Alt+N` 포커스, AltGr 키보드, `Ctrl+Shift+0`과 입력 언어 바꾸기 키, `Shift+F10` · 메뉴 키, 레지스트리에서 읽는 시스템 시계(12시간 · 24시간), 메모 서랍의 반투명 · 강하게 바탕(Windows 11 아크릴)은 확인하지 못했다.
- 두 앱 모두 코드 서명과 공증이 없다. 처음 열 때 macOS Gatekeeper나 Windows SmartScreen을 넘겨야 한다.
- 사례 표는 대부분 두 시험 파일에 같은 내용으로 옮겨 적혀 있다. 스페이스(S1–S22)부터 JSON 파일 하나를 두 시험이 읽게 했고, 앞의 표도 그렇게 옮기는 일이 남았다.
- 메모가 5,000장이거나 1MB인 메모에서 Windows 서랍은 아직 느리다. Mac은 서랍을 처음 열 때 2,000장에서 0.2초쯤 걸린다.
