# 엔지니어링

[← 저장소로](../README.md) · [구조](architecture.md) · [디자인 과정](design-process.md) · [결정 기록](decisions.md)

같은 제품을 Swift와 TypeScript로 두 번 만들면서, 두 앱이 어긋나지 않게 하려고 만든 검사들을 정리했다. 공유 시험 사례, 화면 스냅숏과 크기 훑기, 번역 검사, 대비 검사, 성능 측정 순서다.

## 규모

| | macOS | Windows |
| --- | --- | --- |
| 코어 로직 | Swift 35개 파일, 약 8,000줄 | TypeScript 44개 파일, 약 8,000줄 |
| 앱과 화면 | Swift 64개 파일, 약 21,000줄 | main 약 8,400줄, renderer 약 7,700줄, CSS 2,100줄 |
| 시험 코드 | 약 6,100줄 | 31개 파일, 약 4,600줄 |
| 자동 시험 | 시험 스크립트 15개, 검사 약 300개 | `node:test` 464개 |
| 외부 런타임 의존성 | 없음 (Apple 프레임워크만) | Electron 하나 |

Mac 검사 수는 `mac/scripts/test*.sh` 각각이 마지막에 출력하는 수를 더한 것이다(54 + 6 + 7 + 11 + 18 + 4 + 7 + 13 + 9 + 언어마다 9 + 44 + 13 + 14 + 21 + 58). Windows는 `npm test` 결과다.

## 1. 공유 시험 사례

두 앱은 코드를 나누지 않는다. 대신 기능마다 사례 표를 먼저 쓰고, 두 앱이 표의 모든 줄을 같은 기대 문자열로 통과하게 했다. 개발하는 동안 표는 `intent-cases.md`, `ribbon-cases.md` 같은 문서였다. 공개 저장소에는 그 문서가 없고, 표를 옮겨 적은 두 시험 파일이 기준이다.

입력 줄 사례 1번은 두 앱에서 이렇게 생겼다.

```swift
// mac/Tests/PaperCoreTests/IntentTests.swift
(1, .ko, "내일 3시 회의", [:], ["event \"회의\" 2026-10-09 15:00–16:00 ⟨일정 · 내일(금) 15:00–16:00⟩",
                              "todo \"회의\" reminder 2026-10-09 15:00 ⟨할 일 · 알림 내일 15:00⟩"], "-"),
```

```ts
// windows/test/intent.test.ts
[1, "ko", "내일 3시 회의", {}, "event \"회의\" 2026-10-09 15:00–16:00 ⟨일정 · 내일(금) 15:00–16:00⟩; todo \"회의\" reminder 2026-10-09 15:00 ⟨할 일 · 알림 내일 15:00⟩", "-"],
```

뜻 후보의 순서와 날짜, 칩에 보일 글(⟨…⟩)까지 한 줄에 들어 있어서, 한쪽 구현만 바꾸면 그쪽 시험이 바로 깨진다.

| 사례 묶음 | 번호 | 정하는 것 | macOS | Windows |
| --- | --- | --- | --- | --- |
| 입력 줄 | 1–66 | 할 일, 일정, 타이머, 알람, 메모 중 무엇으로 읽을지와 칩 글 (3개 언어) | `IntentTests.swift` | `intent.test.ts` |
| 입력 줄: 집중 | 101–118 | '보고서 25분 집중'처럼 제목이 붙은 집중 | `IntentTests.swift` | `intent.test.ts` |
| 입력 줄: 편의 | 201–228 | 반복('매일 …'), 상대 시간('30분 뒤 …') | `IntentTests.swift` | `intent.test.ts` |
| 입력 줄: 시간 | 301–324 | '3시부터 5시까지 보고서' 같은 시간 범위 | `TimeBlockTests.swift` | `intent.test.ts`, `timeRange.test.ts` |
| 하루 띠 | R1–R14 | 지금, 다음, 남은 시간, 화면 읽기 문장 | `DayStripTests.swift` | `dayStrip.test.ts` |
| 하루 일정표 | K1–K8, G1–G4, N1–N5 | 키보드, 겹친 블록 배치, 빈 칸에서 새로 만들기 | `DayStripTests.swift` | `dayStrip.test.ts` |
| 타이머 폭과 시간 | T1–T4, C1… | 고정 폭 숫자, 할 일 시간과 알림 | `TimeBlockTests.swift` | `timeRange.test.ts`, `timerWidget.test.ts` |
| 앞으로 탭 | 45줄 + 12 + 3 | 이번 주, 다음 주, 달, 언젠가, 옮김 안내, 빈 화면 | `AheadTests.swift` | `ahead.test.ts` |
| 집중 | F1–F17, FB1–FB4 | 집중 기록 읽기, 새벽 4시 기준 합계, 합치기 | `FocusTests.swift` | `focus.test.ts` |
| 편의 기능 | §1–§6 | 내일로, 저녁 정리, 다시 알림, 초성 검색 | `ConvenienceTests.swift` | `convenience.test.ts` |
| 알람과 타이머 길이 | — | 다음 울림, 시간대(로스앤젤레스, 채텀), '1시간 반', `anderhalf uur` | `AlarmTests.swift`, `DurationTests.swift` | `alarm.test.ts`, `duration.test.ts` |
| 백업 | B0–B5 | 내보낸 뒤 빈 폴더로 바꾸면 같은 파일, 합치기 개수, 쓰다 실패하면 원래대로 | `CoreTests.swift` | `backup.test.ts` |

입력 줄 사례만 136줄이다. 표를 먼저 쓰니 "Windows에서는 다르게 읽힌다" 같은 차이가 구현 전에 드러났다. 한쪽에서 버그를 찾으면 표에 한 줄을 더하고, 그 줄이 다른 쪽에서도 실패하는지 본다.

약점도 있다. 사례 일부(시간 범위, 검색)는 내 시간대 Asia/Seoul을 전제로 쓰였다. 그래서 CI는 두 워크플로 모두 `TZ=Asia/Seoul`로 돌린다. 달력 사례는 처음부터 시간대와 무관하게 써서 로스앤젤레스와 채텀 시간대에서도 통과한다.

## 2. 스냅숏과 크기 훑기

UI 시험은 버튼이 있는지보다 그려진 화면을 본다.

macOS에서는 `mac/scripts/render-design.sh`가 실제 SwiftUI 뷰에 예시 데이터를 넣어 PNG로 저장한다(`Tests/PaperTodoTests/DesignSnapshots.swift`). 한국어, 영어, 네덜란드어와 낮/밤을 모두 그리면 약 1,500장이다. 사용자 목록이나 설정은 읽지도 쓰지도 않는다. `scripts/test-presentation.sh`(44개)는 화면 상태, 키보드, 공유 폴더, 메모 합치기, 백업, 책상, 종이 색, 집중을 확인하고, 손글씨 제목의 마지막 글자가 잘리는지 픽셀로 본다('Ahead', 'coffee', '커피 coffee'). 시험용 앱은 다른 번들 ID와 저장 폴더를 쓰고, 알림은 화면 밖(`PAPERTODO_OFFSCREEN=1`)에 그린다.

Windows에서는 `npm run snapshot`이 모든 창을 화면 밖에서 그리고 크기 훑기(size sweep)를 돌린다.

- 창마다 가장 작은 크기부터 2560 × 1440까지, 배율 125%와 150%, 다른 글꼴(Noto, 붓, 깔끔), 밤 종이로 그린다.
- 크기마다 페이지 안의 검사(`src/main/layoutCheck.ts`)가 옆으로 스크롤되는 상자, 말줄임 없이 잘린 글, 아래가 잘린 글, 창 밖으로 나간 요소, 이웃과 겹친 요소, 상자 밖에서 잘린 손글씨 잉크, 보이지 않는 입력 칸 안내 글을 찾는다. 하나라도 있으면 실패하고, 없으면 `SWEEP OK`를 출력한다.
- 말줄임은 실패로 치지 않고 따로 적어 둔다. 좁은 창에서는 괜찮지만, 넓은 창에서 말줄임이 보이면 자리를 못 쓰고 있다는 뜻이라서다.

잉크 잘림 검사는 처음부터 있던 게 아니다. Caveat와 Kalam의 d, e, f, k 끝이 칸 밖으로 나가 'Ahead'가 'Aheaa'로, 'coffee'가 'coffe'로 보였고, 이걸 Windows 1.22.1과 Mac 1.37.1에서 고치면서 검사를 더했다.

두 플랫폼의 스냅숏이 같은 화면 이름으로 나오니, Mac과 Windows 그림을 나란히 놓고 다른 곳을 찾을 수 있었다. 새 디자인 네 단계를 마친 뒤의 점검 판(Mac 1.37.1, Windows 1.22.1)이 그렇게 나왔다.

## 3. 번역 검사

한국어 원문이 키다. 한국어로 문구를 쓰고 영어와 네덜란드어 표를 채운다. 영어와 네덜란드어 문구는 AI가 초안을 썼고, 아직 원어민 검토를 받지 않았다. 아래 검사는 빠진 번역과 형식 오류를 막을 뿐 문장이 자연스러운지는 보지 못한다.

- macOS의 `scripts/i18n/check.sh`는 컴파일러가 뽑은 모든 문구에 영어와 네덜란드어가 있는지, 자리표시자가 맞는지, 번역을 거치지 않은 한글 문구가 코드에 남았는지 검사한다. `scripts/test-localization.sh`는 세 언어로 앱 문구와 손글씨 글꼴(라틴 글자는 Caveat와 Kalam, 한글은 한국어 손글씨)을 확인한다.
- Windows의 `test/i18nStrings.test.ts`는 `src/main`, `src/renderer`, preload에서 `t()` 밖에 남은 한글과 영어/네덜란드어에 없는 키를 찾아 실패시킨다. 복수형은 `{n|one|many}`로 쓴다.
- 날짜, 시간, 입력 줄, 종이냥 한마디처럼 코어가 만드는 말은 두 앱이 같은 사례로 검사한다. Windows `i18n.test.ts`와 같은 사례를 Mac `CoreTests`가 돌린다.

## 4. 대비 검사

색은 모두 이름 붙은 토큰(종이, 먹 세 단계, 줄, 세이지, 점토, 탭, 테이프)이고 낮과 밤 두 벌이 있다. 두 앱의 최종 색표는 같다.

- macOS `scripts/check-contrast.py`는 낮과 밤의 글자/바탕 38쌍을 표로 출력하고, 하나라도 WCAG AA(본문 4.5:1, 큰 글씨와 UI 3:1)에 못 미치면 실패한다.
- Windows `test/contrast.test.ts`는 같은 표를 같은 기준으로 검사한다.

밤 종이를 넣은 3단계(Mac 1.36.0, Windows 1.21.0)에서는 밤 색만 AA로 검사했고, 낮 색은 4단계(1.37.0, 1.22.0)에서야 맞췄다. 그때 고친 색이다.

| 토큰 | 전 | 후 | 대비 (전 → 후) |
| --- | --- | --- | --- |
| 낮 옅은 먹 (ink3) | #a5a195 | #726e64 | 종이 위 2.45 → 4.83 |
| 낮 점토 글씨 | — | #955842 | 3.97 → 5.32 |
| 낮 세이지 글씨 | — | #546f52 | 세이지 바탕 위 3.93 → 4.57 |
| 낮 빈 체크 칸 테두리 | #b5b0a2 | #908a7b | 2.06 → 3.27 (Windows에서 잰 값) |
| 밤 옅은 먹 | #8a8577 | #9f9989 | 3.96 → 5.13 |
| 밤 체크 칸 테두리 | #77725f | #837e69 | 3.02 → 3.58 |

예전 옅은 먹 #a5a195는 `faint`라는 토큰으로 떼어 장식에만 쓴다. 글자에 잘못 쓰이지 않게 하려고 이름을 따로 붙였다. macOS의 움직임 줄이기와 대비 증가, Windows의 forced-colors도 따른다.

## 5. 성능

같은 도구와 같은 데이터로 고치기 전과 후를 쟀다.

- 데이터: 할 일 150개, 일정 60개, 완료 기록 2,000줄, 메모 80개의 시험용 목록(`mac/scripts/perf-data.py`, `windows/tools/perf-data.mjs`).
- macOS `scripts/perf.sh`: 다른 번들 ID로 시험용 사본을 만들어 그 프로세스만 조작하며 CPU, 메모리, 반응 시간을 잰다. 설치된 앱과 데이터는 건드리지 않고, 끝나면 사본이 쓴 파일을 지운다.
- Windows `npm run perf`: `--demo`로 띄운 앱을 DevTools 프로토콜(렌더러)과 Node 인스펙터(main)로 잰다. 시작 시간, 쉬는 동안 CPU(`app.getAppMetrics`), 메모리, 입력과 탭 전환 지연, 쉬는 동안의 파일 읽기를 본다.

### macOS 1.38 → 1.39

| 항목 | 1.38 | 1.39 |
| --- | --- | --- |
| 노트를 열어 두고 쉴 때 CPU | 61% | 0.7% |
| 노트가 가려지거나 닫혀 있을 때 CPU | 87% | 0.3% |
| 입력 줄 글자 하나 | 0.46초 | 0.01초 |
| 탭 바꾸기 | 몇 초 (밀림) | 0.13초 |
| 검색 열기 | 2.0초 | 0.2초 |
| 켜서 노트가 보일 때까지 | 2.7초 | 1.0초 |
| 10분 쓴 뒤 메모리 | 213MB | 136MB |

가장 큰 원인은 하루 띠였다. 1.34에서 들어간 '지금' 선은 숨 쉬듯 깜빡였는데, 깜빡이는 동안 노트 전체가 매 프레임 다시 그려지고 있었다. 노트를 열어 두면 CPU를 45–85% 썼고, 가려져 있으면 더 썼다. 성능을 재 보기 전까지는 몰랐다. 1.39에서 깜빡임을 Core Animation에 넘겼고, 1.40에서 띠를 새로 그리면서 '지금' 눈금은 아예 깜빡이지 않게 했다. 지금은 분이 바뀔 때와 내용이 바뀔 때만 다시 그린다.

나머지 원인은 이랬다.
- 노트 창이 크기를 정하려고 목록 전체를 매번 다시 쟀다.
- 입력 줄이 글자를 칠 때마다 같은 규칙을 수십 번 새로 만들었다. 이제 한 번 만들고, 같은 글에는 앞의 결과를 다시 쓴다.
- 완료 기록 2,000줄을 읽으면서 날짜마다 날짜 읽는 도구를 두 개씩 새로 만들었다. 검색, 기록, 책상을 처음 열 때 1초 넘게 멈춘 이유다.
- 목록이 화면 밖의 줄까지 만들었고, 탭 줄은 도구 단추를 매번 다시 그렸다.

### Windows 1.23 → 1.24 → 1.25

| 항목 | 1.23 | 1.24 | 1.25 |
| --- | --- | --- | --- |
| 노트를 띄워 두고 쉴 때 CPU | 5.7% | 1.5% | — |
| 같은 날 다시 잰 쉴 때 CPU | — | 1.17% | 0.22% |
| 노트를 숨겼을 때 CPU | — | 0.18% | 0.07% |
| 알람이 울린 뒤 CPU | 9.2% | 0.5% | 같은 수준 |
| 타이머가 돌 때 CPU | 6.5% | 4.4% | 1.91% (같은 날 잰 1.24는 4.95%) |
| 쉬는 동안 파일 통째 읽기 | 분당 10번 | 0번 | 0번 |
| 10분 쓴 뒤 메모리 | 692MB | 457MB | — |
| 앞으로 탭으로 넘어가기 | 86ms | 53ms | — |
| 체크 → 애니메이션 | 27ms | 20ms | — |

Windows에도 같은 종류의 문제가 있었다. 하루 띠의 '지금' 점이 매 프레임 그려졌고, 숨긴 펫 창에서도 숨쉬기 애니메이션이 돌았다. 알람이 울린 뒤에는 숨겨 둔 쪽지의 물결이 계속 움직였다. 앱 상태를 모든 창에 보냈고, 바뀌지 않은 줄과 띠와 탭을 다시 그렸고, 공유 폴더를 확인할 때마다 파일을 통째로 읽었다. 지금은 파일 크기와 수정 시각을 먼저 보고 바뀐 것만 읽는다. 펫이 나와 있을 때의 CPU(약 4–7%)는 줄이지 못했다.

> 숫자는 모두 내 Mac 한 대에서 잰 값이고, 그날 컴퓨터가 얼마나 바빴는지에 따라 조금씩 달라진다. Windows 빌드의 숫자도 macOS 위 Electron에서 쟀다. 실제 Windows PC에서 잰 숫자는 없다.

## 6. 빌드와 CI

```sh
# macOS (Swift 6, macOS 14 이상)
cd mac
swift build
./scripts/test.sh                 # 코어 회귀 (54)
./scripts/test-intent.sh          # … 그 밖의 test-*.sh
python3 scripts/check-contrast.py
./scripts/i18n/check.sh
./scripts/build.sh                # dist/종이냥.app (로컬 서명)

# Windows (Node 22 이상)
cd windows
npm ci
npx tsc --noEmit -p .
npm test                          # 464
npm run dist                      # Windows 설치 파일 (macOS에서도 만들 수 있다)
```

GitHub Actions 워크플로는 두 개다. `.github/workflows/ci.yml`(README 배지)은 Windows 앱의 타입 검사와 시험 464개를 macOS 러너에서 돌린다. `.github/workflows/mac.yml`은 Xcode 26 러너에서 Mac 앱을 빌드하고 코어 시험, 대비 검사, 번역 검사를 돌린다. Xcode 26 이미지가 없으면 이 워크플로만 실패하도록 둘을 나눴다.

## 아직 못 한 것

- Windows 앱은 macOS 위의 Electron에서 모든 화면과 동작을 확인하고 설치 파일을 만들었다. 실제 Windows PC에서는 한 번도 돌려 보지 않았다. 설치 과정, 알림 영역, 클릭 통과, `Ctrl+Alt+N` 포커스, AltGr 키보드는 확인하지 못했다.
- 두 앱 모두 코드 서명과 공증이 없다. 처음 열 때 macOS Gatekeeper나 Windows SmartScreen을 넘겨야 한다.
- 사례 표는 두 시험 파일에 같은 내용으로 옮겨 적혀 있다. 표를 JSON 같은 파일 하나로 두고 두 시험이 읽게 했으면 옮겨 적는 실수를 막을 수 있었다.
