# 결정 기록

[← 저장소로](../README.md) · [구조](architecture.md) · [엔지니어링](engineering.md) · [디자인 과정](design-process.md)

앱의 모양을 크게 바꾼 결정 열 개예요. 각각 그때 상황, 고른 것, 얻은 것과 대가 순서로 적었어요. 제목은 정한 내용 그대로라 다른 문서가 링크로 걸고 있어요.

---

## ADR 1: 서버 없이 내 컴퓨터의 파일에 저장한다

종이냥은 한 사람이 자기 컴퓨터 한두 대에서 쓰는 앱이에요. 계정과 서버를 두면 로그인, 서버 비용, 개인정보 처리가 따라와요.

그래서 모든 데이터를 저장 폴더의 JSON 파일(`todos.json`, `events.json`, `focus.jsonl` …)에 둬요. 여러 기기에서 쓰려면 사용자가 iCloud Drive, OneDrive, Dropbox 폴더를 저장 위치로 골라요. 파일을 옮기는 건 클라우드 앱이고, 앱은 다른 기기가 쓴 파일을 받아들이는 일만 해요.

얻은 것: 인터넷이 없어도 그대로 동작해요. 파일은 사람이 읽을 수 있고, `.jongi` 백업 파일 하나로 Mac과 Windows 사이를 옮겨요.

대가: 동시 편집을 앱이 직접 다뤄야 했어요. 저장 직전에 다시 읽고 그 위에 바꾸기, 메모의 3-way 합치기, 알림을 기기마다 따로 기억하기를 만들었고, 이 규칙들은 두 앱이 같은 사례로 검사해요. 저장은 늘 임시 파일에 쓴 뒤 바꿔 끼우고, 읽을 수 없는 파일은 덮어쓰지 않고 따로 보관해요.

## ADR 2: Google 연동을 뺐다

결론부터 말하면, 잘 동작하던 연동을 뺐어요. Mac 1.26–1.30, Windows 1.11–1.15의 다섯 판에 걸쳐 Google 캘린더 읽기와 쓰기, 달력 창, Google Tasks 양방향 맞추기를 만들었고, Mac에는 Apple 캘린더 읽기도 넣었어요. 설치형 앱 OAuth(loopback + PKCE), 권한 범위를 나눠 처음 쓸 때 묻기, 토큰 보관(Mac은 권한 600 파일, Windows는 DPAPI)까지 갖췄어요. 가짜 Google 서버로 연결부터 해제까지 흐름 전체도 시험했어요.

그런데 나는 개인 일정과 업무를 확실히 나누고 싶었어요. 업무를 개인 공간에 들이고 싶지 않았고, 반대도 마찬가지였어요. 앱을 같이 써 본 사람들도 같은 말을 했어요. 쓰기 전 단계도 문제였어요. 사용자가 Google Cloud에서 OAuth 클라이언트 파일을 직접 만들어 불러와야 했어요. ADR 1의 ‘서버 없음’과도 맞지 않았어요.

Mac 1.31.0, Windows 1.16.0에서 연동을 모두 빼고, 일정은 앱 안에 적는 자체 일정(`events.json`)으로 바꿨어요. 달력 창, 일정 알림, 종이냥의 일정 이야기는 자체 일정 위에 남겼어요.

얻은 것: 클라이언트 파일 설정, 계정 연결, 권한 묻기, 맞추기 충돌 규칙이 모두 없어졌어요. 일정이 할 일과 같은 폴더에 있으니 공유 폴더, 백업, 검색, 하루 띠가 일정을 따로 다루지 않아도 돼요.

대가: 다른 캘린더의 일정은 직접 옮겨 적어야 해요. 예전 연결 정보 파일(`google.json` 등)은 시작할 때 지워서 토큰을 남기지 않아요.

## ADR 3: Windows 앱은 Electron으로 만든다

Mac 앱은 SwiftUI + AppKit으로 먼저 자리를 잡았어요. Windows에서도 손글씨 글꼴, 종이 질감, 와시 테이프 탭, 투명한 펫 창을 똑같이 내야 했고, 개발과 화면 확인은 Mac 한 대에서 했어요.

Electron + TypeScript를 골랐고, UI 라이브러리 없이 HTML과 CSS로 그려요. 화면과 상관없는 규칙은 `src/core/`에 순수 TypeScript로 두어 Node에서 바로 시험해요.

얻은 것: 종이 디자인을 CSS로 거의 그대로 옮겼어요. 색 토큰은 `:root` 변수 한 벌로 관리하고, 밤 종이는 `data-paper="night"`로 바꿔요. Mac에서 Windows 화면을 그리고(`npm run snapshot`), 크기 훑기로 레이아웃을 검사하고, 설치 파일까지 만들어요.

대가: 메모리와 설치 크기가 커요. 1.23에서 10분 쓴 뒤 메모리가 692MB였어요. 1.24에서 457MB로, 쉴 때 CPU는 5.7%에서 1.5%로 줄였고, 1.25에서 같은 날 다시 재 보니 1.17%에서 0.22%가 됐어요. 더 큰 대가는 Mac에서만 개발했다는 점이에요. 실제 Windows PC에서는 아직 돌려 보지 않았고, 알림 영역, 클릭 통과, AltGr 키보드처럼 거기서만 드러나는 문제는 확인하지 못했어요.

## ADR 4: 코드 대신 시험 사례를 나눈다

같은 규칙(날짜 읽기, 하루 띠, 앞으로 탭, 집중 기록 …)을 Swift와 TypeScript에서 두 번 구현해야 했어요. 공통 코어를 한 언어로 만들어 다른 쪽에 붙이는 방법도 있었어요. C나 Rust로 짜서 FFI(다른 언어 함수 부르기)로 부르거나, Mac의 JavaScriptCore에서 TypeScript 코어를 돌리는 식이에요.

각 앱은 자기 언어로 쓰기로 했어요. 대신 기능마다 사례 표를 먼저 만들고, 두 앱이 모든 줄을 같은 기대 문자열로 통과하게 해요(입력 줄 136줄, 하루 띠 R/K/G/N/T, 집중 F/FB …). 종이냥 한마디처럼 같은 문장이 필요한 곳은 파이썬 파일 하나에서 두 앱의 코드를 만들어요.

얻은 것: 빌드가 단순해요. Mac은 외부 의존성이 없고, Windows 코어는 Node만 있으면 시험할 수 있어요. 사례 표가 사양서 역할을 해서 두 앱의 차이가 구현 전에 드러나고, 한쪽에서 찾은 버그는 표에 한 줄을 더해 다른 쪽에서도 확인해요.

대가: 구현은 여전히 두 번이에요. 표가 줄여 주는 건 두 구현이 같은지 확인하는 일이에요. 그리고 표가 두 시험 파일에 옮겨 적혀 있어서, 표를 고칠 때도 두 번 고쳐요.

## ADR 5: 종이 디자인 시스템

기능이 늘면서 창마다 모양이 달라졌어요. 시스템 경고창, 설정 창, 알람 카드, 색 띠가 있는 머리 영역이 제각각이었어요. 밤 모드를 넣으려니 흩어진 색을 하나씩 찾아 바꿔야 했어요.

새 디자인 네 단계(Mac 1.34–1.37, Windows 1.19–1.22)를 거치며 이렇게 정했어요.
- 색은 이름 붙은 토큰(종이, 먹 세 단계, 줄, 세이지, 점토, 탭, 테이프)으로 쓰고, 낮과 밤 두 벌을 둬요. 세이지는 지금, 끝냄, 선택에만, 점토는 곧, 늦음, 지우기에만 써요.
- 떠 있는 창은 모두 테이프로 붙인 종이 쪽지 모양으로 맞춰요. 테이프 색이 종류를 나타내고, 확인 단추는 하나, 위험한 동작은 왼쪽에 점토색으로 둬요.
- 할 일 제목은 손글씨, 조작과 숫자는 시스템 글꼴로 써요. 숫자는 고정 폭이에요.
- 낮과 밤의 모든 글자 · 바탕 쌍 가운데 하나라도 WCAG AA를 넘지 못하면 검사가 실패해요(이 규칙은 4단계에서 낮 색까지 넓혔어요).

3단계에서 밤 종이를 넣을 때는 토큰의 두 번째 벌만 더하면 됐어요. 두 앱의 최종 색표는 같고, [디자인 과정](design-process.md#종이-디자인-시스템)에 표로 있어요.

## ADR 6: 하루는 새벽 4시에 바뀐다

자정을 넘겨 일하는 사람에게 00:30의 할 일은 내일 일이 아니에요.

두 앱 모두 하루의 경계를 새벽 4시로 둬요. 완료 기록, 반복, 마감, 집중 합계, 하루 띠가 같은 기준을 써요. 밤 일정이 있으면 하루 띠가 새벽 4시까지 늘어나요.

그래서 `23:00–01:00` 같은 할 일 시간도 하루 안에 들어가요. 날짜 경계 사례는 공유 시험 사례에 함께 있어요.

## ADR 7: 메모 폴더는 memos.json 밖의 새 파일에 둔다

메모 탭을 화면 끝의 메모 서랍으로 옮기면서(Mac 1.43, Windows 1.28) 메모에 폴더와 고정이 생겼어요. 그런데 공유 폴더에서는 한 기기만 새 버전이고 다른 기기는 옛 버전일 수 있어요. Mac은 `Codable`로 메모를 읽고 써서, 옛 버전이 `memos.json`을 저장하면 모르는 칸(폴더)을 지워요. 메모에 `folder` 칸을 더하면, 옛 기기에서 메모 하나를 고치는 순간 모든 메모의 폴더가 사라질 수 있었어요.

그래서 `memos.json`의 모양은 그대로 두고, 폴더 목록과 메모마다의 자리(폴더, 고정, 1.44의 메모 종이)를 새 파일 `memo-folders.json`에 둬요. 메모 id로 둘을 이어요.

얻은 것: 옛 버전이 `memos.json`을 저장해도 폴더 정보는 남아요. 옛 버전이 만든 메모는 자리가 없으니 '메모' 폴더에 보여요. 1.42까지 메모 탭에 있던 메모는 하나도 옮기거나 바꾸지 않고 '메모' 폴더에 그대로 보여요. 백업(.jongi)에도 같은 파일이 들어가요.

대가: 파일이 하나 늘었고, 두 파일이 어긋날 수 있어요. 지운 폴더를 가리키는 자리는 '메모' 폴더로 봐요. 폴더는 id로, 자리는 나중에 고친 쪽으로 합쳐요. 1.44/1.29부터는 이 파일의 모르는 항목을 읽은 그대로 다시 써서, 더 새 버전이 더한 칸(정렬, 메모의 종이)도 지우지 않아요. 다만 1.43/1.28이 이 파일을 다시 쓰면 정렬과 메모의 종이는 빠질 수 있어요(폴더, 고정, 메모는 그대로예요).

## ADR 8: Claude 연결은 서버 없는 확장으로, 기본은 꺼짐

Claude와 대화하면서 할 일을 넣고 고치고 싶었어요(Mac 1.42, Windows 1.27). 하지만 AI가 내 목록을 바꾸는 건 조심해야 했어요. 잘못 알아들은 한마디로 할 일이 사라지거나 바뀌면 안 되고, ADR 1의 ‘서버 없음’도 지켜야 했어요.

Claude 데스크톱과 Claude Code가 쓰는 MCP 확장(AI 앱이 다른 프로그램을 도구로 쓰는 연결) 하나를 만들고, 이렇게 정했어요.
- 처음에는 꺼져 있어요. 책상의 AI 연결에서 켜야 확장이 읽고 써요. 꺼져 있으면 모든 도구가 ‘설정에서 켜 주세요’만 답해요.
- 보기와 넣기는 바로 해요. 같은 날 같은 제목은 두 번 넣지 않아요.
- 고치기는 두 단계예요. 바뀌기 전과 후를 대화에 보여 주고(`preview_changes`), 사용자가 ‘응’ 하면 고쳐요(`apply_changes`). 그사이 앱에서 그 항목을 바꿨으면 고치지 않아요. 지우기, 반복 일정과 알람 고치기는 하지 않아요.
- Claude가 한 일은 기기마다 `ai-log.jsonl`에 남아요. 앱은 '되돌리기' 안내, 그날의 'Claude' 도장, 책상의 '최근 AI 작업'으로 보여 주고, 하나씩 되돌려요. 그새 바뀐 항목은 되돌리지 않아요.
- 서버를 켜 두지 않아요. Claude가 필요할 때 확장을 실행해요. 확장은 Windows 앱 폴더에서 TypeScript로 만들고, Mac 앱은 같은 파일을 앱 안에 넣어요.

얻은 것: 계정, 서버, 토큰이 없어요. 켜지 않으면 아무 일도 없고, 켜도 고치기 전에는 늘 물어요. 확장 하나를 두 앱이 함께 써서 도구의 말과 규칙이 같아요.

대가: 앱과 확장이 같은 파일을 쓰게 됐어요. 쓰기 직전에 다시 읽고, `ai-write.lock`을 잠깐 잡아 같은 순간에 쓰지 않아요. 시험용 사본에서 앱과 Claude가 20개씩 동시에 넣어도 하나도 잃지 않는 것을 확인했어요. Claude Code 연결과 `.mcpb` 설치에는 Node나 Claude 데스크톱이 필요해요.

## ADR 9: 할 일 스페이스는 todo-spaces.json에 따로 둔다

할 일을 회사, 집, 공부처럼 나누고 싶었어요(Mac 1.45, Windows 1.30). 가장 쉬운 길은 할 일마다 `space` 칸을 더하는 것이었어요. 그런데 ADR 7과 같은 문제가 있었어요. Mac 1.44까지는 `todos.json`을 `Codable`로 읽고 써서 모르는 칸을 지워요. Windows 1.29까지도 아는 칸만 골라 읽고 읽은 것만 쓴다는 것을 구현 전에 시험으로 확인했어요. 공유 폴더의 다른 기기가 옛 버전이면, 그 기기에서 할 일 하나를 체크하는 순간 모든 할 일의 스페이스가 사라져요.

그래서 `todos.json`은 그대로 두고, 스페이스 목록과 할 일마다의 자리를 옆의 새 파일 `todo-spaces.json`에 둬요. 할 일 id로 둘을 이어요.
- 스페이스는 id로 합치고 `updatedAt`이 늦은 쪽이 이겨요. 자리는 할 일마다 `at`이 늦은 쪽이 이겨요. 같은 초면 파일에 이미 있던 쪽을 둬요.
- ‘스페이스 없음으로 옮김’도 `space: null`로 남겨요. 지우면 합칠 때 옛 자리가 되살아나거든요.
- 지운 스페이스와 없어진 할 일의 자리는 30일 뒤 저장할 때 빼요. 모르는 칸은 맨 위, 스페이스, 자리 모두 읽은 그대로 다시 써요.
- 두 앱이 같은 바이트를 써요: 키 정렬, 들여쓰기 2칸, 초 단위 UTC.
- 한 스페이스만 보기는 기기마다의 설정이고, 파일에 넣지 않아요.

사례 표도 이번에 처음으로 파일 하나에 뒀어요. `docs/plans/spaces-cases.json`의 S1–S22를 Mac `scripts/test-spaces.sh`와 Windows `npm test`가 같이 읽어요. ADR 4의 대가로 적은 ‘두 시험 파일에 옮겨 적기’를 이 기능부터 덜었어요.

얻은 것: 옛 버전이 할 일을 저장해도 스페이스는 남아요. 옛 버전이 만든 할 일은 ‘스페이스 없음’으로 보여요. 스페이스를 하나도 만들지 않으면 파일도 화면도 1.44/1.29와 같아요.

대가: 할 일 하나의 정보가 두 파일에 나뉘어요. 옛 버전이 할 일을 지우면 남은 자리는 30일 뒤에야 빠져요. 반복 규칙, 앞으로 탭, 완료 기록의 스페이스는 2단계로 미뤘어요.

## ADR 10: 화면의 말은 글쓰기 가이드 하나를 따른다

UI/UX 점검을 하면서 화면 모양만큼 말도 어긋나 있다는 걸 알았어요. 같은 것을 곳마다 다른 이름으로 불렀고(‘종이냥 끝내기’ · ‘종이냥 종료’, ‘완료 숨기기’ · ‘완료한 일 숨기기’), 저장 오류 여덟 개는 무엇을 하면 되는지 말하지 않고 긴 경로만 붙였어요. 버튼에 ‘끝냄’ 같은 상태말이 있었고, 고양이는 ‘서둘러요!’처럼 재촉했어요. 영어 · 네덜란드어도 같은 것을 다르게 불렀어요.

토스의 공개된 라이팅 원칙(다섯 가치, 여덟 점검)을 종이냥에 맞게 고쳐 [글쓰기 가이드](writing.md)를 만들고, 낱말은 [용어표](terms.md) 한 곳에 모았어요. 문구를 고칠 때는 이 둘을 먼저 봐요.
- 해요체로 쓰고, 느낌표는 축하할 때만 써요. ‘저’라고 말하는 건 고양이뿐이에요.
- 버튼은 동사로, 토스트는 ‘[무엇을] [어떻게] 했어요 · 되돌리기’로 써요. 확인 쪽지는 무엇이 바뀌고 되돌릴 수 있는지 말해요.
- 오류는 무엇을 못 했나 → 지금 상태 → 할 일 순서로 써요. 경로와 오류 번호는 붙이지 않아요.
- 파일 이름과 개발자 말은 설정과 오류에 쓰지 않고, 도움말 ‘알아 두기’와 개발 문서에만 써요.
- ko · en · nl을 같이 고치고, 렌더해서 잘림을 봐요.

먼저 문구 점검에서 고칠 문구를 모아 이슈로 나눈 뒤, 두 앱을 같은 판(Mac 1.45, Windows 1.30)에서 같이 고쳤어요.

얻은 것: 두 앱과 세 언어의 말이 같은 표를 따라요. 새 문구를 쓸 때 고를 기준이 문서로 있어요.

대가: 손에 익은 말이 바뀌었어요(‘끝냄’ → ‘끝내기’, ‘내일로 미루기’ → ‘내일 하기’). 영어와 네덜란드어는 아직 원어민이 보지 않았어요.
