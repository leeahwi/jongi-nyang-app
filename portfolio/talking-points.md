# 면접 질문과 답

말로 하는 답이라 해요체로 적었다. 각 답은 상황, 내 역할, 한 일과 이유, 결과, 그 뒤 바뀐 것 순서이고 1–2분 분량이다. 괄호 안은 근거 문서다.

---

**1. 이 프로젝트를 소개해 주세요.**

macOS와 Windows용 할 일 앱이에요. 일할 때도 집에서도 할 일이 쌓이는데, 편하게 적고 한눈에 볼 앱이 없었어요. 필요한 기능은 유료였고, 할 일, 타이머, 일정을 보려면 앱 두세 개를 오가야 했어요. 그래서 평소엔 작은 아이콘으로 있다가 필요할 때 펼쳐지는 포스트잇 같은 앱을 만들었어요. 처음엔 오늘 할 일만 적는 작은 Mac 메모장이었고, 지금은 Mac 1.40.1, Windows 1.25.1까지 냈어요. 혼자 만들었고 Claude Code와 페어 프로그래밍을 했어요. Mac은 Swift와 SwiftUI, Windows는 Electron과 TypeScript로 따로 만들었는데, 기능마다 사례 표를 먼저 쓰고 두 앱의 시험이 같은 문자열을 통과하게 해서 동작을 맞췄어요. 입력 줄 사례만 136줄이에요. 새 디자인 네 단계도 두 앱에 같은 버전 단위로 넣었어요. (`docs/engineering.md`)

**2. 왜 같은 앱을 두 번 만들었어요? 크로스플랫폼 하나로 하면 되잖아요.**

Mac 앱이 먼저 있었어요. 메뉴 막대, 투명한 펫 창, Core Animation 같은 걸 쓰고 있어서 Swift를 버리기 어려웠어요. Windows는 종이 디자인을 CSS로 거의 그대로 옮길 수 있는 Electron을 골랐어요. 공통 코어를 C나 Rust로 짜서 FFI로 붙이거나, Mac에서 JavaScriptCore로 TypeScript 코어를 돌리는 방법도 있었는데, 빌드가 복잡해지는 대신 각자 언어로 쓰고 사례 표를 나누기로 했어요. 같은 규칙을 두 번 구현하는 비용은 그대로 남았어요. (`docs/decisions.md` ADR 3, 4)

**3. '사례 표를 나눈다'는 게 구체적으로 뭐예요?**

기능마다 입력과 기대 결과를 한 줄로 적은 표예요. `내일 3시 회의`라면 첫 번째 후보는 일정, 두 번째는 할 일이고 칩에는 '일정 · 내일(금) 15:00–16:00'이 보여야 한다는 것까지 한 줄에 들어가요. Swift 시험과 TypeScript 시험이 같은 줄을 같은 문자열로 통과해야 해요. 한쪽에서 버그를 찾으면 표에 한 줄을 더하고, 다른 쪽에서도 실패하는지 봐요. 아쉬운 건 표가 두 시험 파일에 옮겨 적혀 있다는 점이에요. 다시 하면 JSON 파일 하나로 두고 두 시험이 읽게 할 거예요. (`docs/engineering.md` 1장)

**4. 가장 큰 성능 문제는 뭐였어요?**

기능을 넣던 중에 Mac 1.38.1을 재 봤어요. `perf.sh`로 다른 번들 ID의 시험용 사본을 띄우고 할 일 150개, 일정 60개, 기록 2,000줄, 메모 80개를 고정해 넣고 그 프로세스만 재요. 아무것도 안 하는데 노트를 열어 두면 61%, 가려 두면 87%였어요. 시험은 다 통과한 상태였어요. 원인은 하루 띠의 깜빡이는 '지금' 선이었어요. 그 선 때문에 노트 전체가 매 프레임 다시 그려지고 있었어요. 모양은 그대로 두고 깜빡임만 Core Animation에 넘겼고, 1.39에서 0.7%가 됐어요. 같은 판에서 입력 지연 0.46초가 0.01초로, 시작 시간 2.7초가 1.0초로 줄었어요. 1.40에서 하루 띠를 새로 그릴 때는 깜빡임을 아예 뺐어요. (`portfolio/troubleshooting.md` 1번)

**5. 디버깅이 어려웠던 버그가 있어요?**

Mac 1.40.0을 쓰다가 제가 찾았어요. 집중을 마치고 집중 카드의 ×를 누르니 앱 전체가 클릭을 안 받았어요. 화면엔 아무 창도 안 보였고요. 겪은 대로 Claude Code에 알리고 원인을 추적해 보니, 프로세스 샘플링과 창 목록에서 "그만둘까요?" 확인 쪽지가 0×0 크기의 모달 창으로 떠 있었어요. 다른 창의 SwiftUI 버튼 동작 안에서 쪽지를 띄우면 아직 크기를 재지 못해서 0×0이 나오는 게 원인이었어요. 쪽지를 누른 동작이 끝난 뒤에 띄우고, 크기를 못 재면 520 × 420 임시 크기로 먼저 그리게 고쳤어요. 공통 코드라 다른 확인 쪽지도 같이 고쳐졌어요. 스냅숏이 약 1,500장 있었지만, 이 버그는 실제 앱에서 버튼을 눌러야 드러났어요. 같은 판에서 30분짜리 할 일로 집중하면 29분으로 시작하던 것도 고쳤는데, 그것도 쓰다가 본 거예요. (`portfolio/troubleshooting.md` 2번)

**6. 성능은 어떻게 쟀어요?**

같은 데이터, 같은 도구로 전후를 쟀어요. Mac은 `perf.sh`가 시험용 사본만 조작하면서 `perf-probe.swift`로 CPU, 깨어나는 횟수, 메모리, 키 입력부터 반응까지 시간을 읽어요. 설치된 앱과 실제 데이터는 건드리지 않아요. Windows는 `perf.mjs`가 DevTools 프로토콜로 렌더러를, Node 인스펙터로 main 프로세스를 재요. 한계도 있어요. 전부 제 Mac 한 대에서 잰 값이라 그날 부하에 따라 조금씩 달라지고, Windows 숫자도 macOS 위 Electron에서 잰 거예요. (`docs/engineering.md` 5장)

**7. UI는 어떻게 시험했어요?**

그려서 봐요. Mac은 실제 SwiftUI 뷰를 3개 언어와 낮/밤으로 약 1,500장 그려요. Windows는 창마다 가장 작은 크기부터 2560 × 1440까지, 배율 125%와 150%, 다른 글꼴로 훑으면서 잘린 글, 겹친 요소, 창 밖으로 나간 요소를 찾고 하나라도 있으면 실패해요. 영어 손글씨에서 'Ahead'가 'Aheaa'로 잘려 보인 적이 있어서, 그 뒤로 잉크가 칸 밖에서 잘리는지도 검사해요. (`docs/engineering.md` 2장)

**8. 접근성은 어떻게 챙겼어요?**

색을 이름 붙은 토큰으로 모으고, 낮과 밤의 글자/바탕 38쌍이 WCAG AA를 못 넘으면 검사가 실패하게 했어요. 처음엔 밤 색만 검사했고 낮 색은 4단계(Mac 1.37.0)에서야 맞췄어요. 그때 옅은 글씨가 2.45:1이었던 걸 4.83:1로 올렸어요. 하루 일정표까지 키보드로 다룰 수 있고, 화면 읽기 프로그램은 하루 띠를 '지금 팀 회의, 40분 남음' 같은 한 문장으로 읽어요. (`docs/engineering.md` 4장)

**9. 서버 없이 여러 기기 동기화는 어떻게 해요?**

동기화는 iCloud Drive, OneDrive, Dropbox 같은 클라우드 앱에 맡기고, 앱은 다른 기기가 쓴 파일을 받아들이는 일만 해요. 저장 직전에 파일을 다시 읽고 그 위에 바꾸고, 같은 메모는 마지막으로 함께 본 글을 기준으로 줄과 글자 단위 3-way 합치기를 해요. 한글 조합 중이면 끝날 때까지 기다리고요. 알람 목록은 함께 쓰지만 울린 기록은 기기마다 따로 둬요. 저장은 항상 임시 파일에 쓰고 바꿔 끼워요. (`docs/architecture.md`)

**10. 만든 기능을 뺀 적이 있어요?**

Google 캘린더와 Tasks 연동이요. Mac 1.26부터 1.30까지 다섯 판에 걸쳐 OAuth(loopback + PKCE), 권한을 나눠 묻기, 가짜 Google 서버로 흐름 전체 시험까지 만들었어요. 잘 동작했는데, 저는 개인 일정과 업무를 확실히 나누고 싶었어요. 업무를 개인 공간에 들이고 싶지 않았고 반대도 마찬가지였어요. 같이 써 본 사람들도 같은 말을 했어요. 게다가 쓰려면 사용자가 Google Cloud에서 클라이언트 파일을 직접 만들어야 했고, "계정도 서버도 없다"는 원칙과도 안 맞았어요. 1.31.0에서 빼고 앱 안의 자체 일정으로 바꿨어요. 대신 다른 캘린더의 일정은 직접 옮겨 적어야 해요. (`docs/decisions.md` ADR 2)

**11. 디자인은 어떻게 정했어요?**

AI에게 여러 안을 나란히 놓은 페이지로 받고, 제가 고르거나 섞었어요. 기준은 한눈에 알아볼 수 있는지였어요. 타이머와 알람은 시간이 또렷이 보여야 하지만, 화면에 늘 떠 있으니 크기와 모양이 방해가 되면 안 됐어요. 고른 안은 화면보다 먼저 말과 숫자로 적었어요. 몇 분 전부터 붉게 바뀌는지, 좁은 창에서 무엇을 줄이는지 같은 것들이요. 그게 사례 표가 됐어요. 새 디자인은 네 단계로 나눠 두 앱에 같은 버전으로 넣었고, 마지막에 두 앱을 화면마다 나란히 놓고 점검한 판(Mac 1.37.1, Windows 1.22.1)을 따로 냈어요. 하루 띠는 세 번 다시 그렸는데, 쓰다 보니 하루 전체보다 지금 무엇을 하고 얼마나 남았는지가 필요해서 3차에서 그걸 크게 보여 주고 하루 전체는 누르면 펼쳐지게 했어요. 카드 모양도 뺐어요. 카드는 AI가 만든 디자인마다 나오는 모양이라 그 티를 빼고, 사람들이 익숙한 대로 시간이 왼쪽에서 오른쪽으로 흐르는 막대를 남겼어요. (`docs/design-process.md`)

**12. AI를 얼마나 썼어요? 본인이 한 건 뭐예요?**

저는 기획과 기능, 쓰기 편한지와 실제로 쓸모가 있는지에 집중했어요. 구현 방법과 디자인 시안은 AI가 여러 개 제안했는데, 그대로 받지 않고 먼저 구현 계획을 미리보기로 보여 달라고 한 뒤 무엇을 넣을지 정했어요. 코드, 시험, 측정 스크립트, 번역은 많은 부분 AI가 초안을 썼고, 고양이 그림은 이미지 생성 도구로 만들어 제가 골랐어요. 매일 앱을 쓰면서 필요한 기능(할 일 시간 알림, 언젠가로 넘겼다가 오늘로 가져오기, 메모 탭)을 넣자고 했어요. 탭 끝이 잘리는 것, 알람 창이 밋밋한 것, 집중 뒤 앱이 멈추는 것, 30분이 29분으로 보이는 것처럼 쓰다가 찾은 버그도 고치게 하고 결과를 검토했어요. 영어와 네덜란드어는 아직 원어민 검토를 받지 못했어요. AI가 빨리 많이 쓸수록 실패를 기계가 알려 주는 검사가 더 필요해서, 저장소의 검사 대부분이 그렇게 생겼어요. (`portfolio/ai-collaboration.md`)

**13. 왜 종이와 고양이예요?**

다들 화면에 익숙해도, 플래너에 할 일을 적고 그렇게 공부하던 경험은 아직 강하다고 봤어요. 종이에 적는 느낌이 나면 할 일을 관리하는 게 더 손에 잡힐 거라고 생각했어요. 고양이는 딱딱한 디자인이 쉽게 무시되고 금방 지루해져서 넣었어요. 네덜란드어는 벨기에와 네덜란드에 있는 친구들 때문에 넣었어요.

**14. 직접 써 보니 무엇이 달라졌어요?**

단축키로 바로 적고, 한곳에서 다 보고, 매일 알림을 받으니 할 일을 놓치는 일이 줄었고 일정 확인이 훨씬 편해졌어요. 제가 가장 많이 쓰는 건 할 일 넣기이고 일정도 자주 넣어요. 쓰다 보니 필요한 것도 생겼어요. 정한 시각에 알려 주는 할 일 알림, 오늘 못 할 일을 언젠가로 넘겼다가 다시 오늘로 가져오기(Mac 1.17), 할 일과 따로 적는 메모 탭(Mac 1.15)은 제가 쓰다가 넣자고 한 것들이에요. 타이머와 뽀모도로는 저는 잘 안 써서, 앱을 나눠 쓰는 지인 몇 명에게 의견을 받고 있어요.

**15. 다시 한다면 무엇을 다르게 하겠어요?**

세 가지예요. Windows 판은 처음부터 실제 Windows PC에서 돌려 보겠어요. 지금은 macOS 위 Electron에서만 확인해서 알림 영역, 클릭 통과, AltGr 키보드는 확인하지 못했어요. 사례 표는 시험 두 곳에 옮겨 적지 않고 파일 하나로 두겠어요. 그리고 시험을 시간대와 무관하게 쓰겠어요. 지금은 일부 사례가 Asia/Seoul을 전제로 해서 CI를 `TZ=Asia/Seoul`로 돌려요.
