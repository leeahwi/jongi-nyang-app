# 문제 해결 기록

[English](troubleshooting.en.md)

종이냥을 만들며 겪은 문제 네 개를 상황, 원인 추적, 대안, 선택과 이유, 결과, 그 뒤 순서로 적었다. 숫자는 [`mac/CHANGELOG.md`](../mac/CHANGELOG.md), [`windows/CHANGELOG.md`](../windows/CHANGELOG.md)와 같다.

## 1. 쉬고 있는데 CPU 61% (Mac 1.38.1 → 1.39.0)

| 순서 | 내용 |
| --- | --- |
| 상황 | 기능을 계속 넣던 중 Mac 1.38.1을 재 봤다. 고정된 시험 데이터를 넣은 시험용 사본에서, 아무것도 하지 않는데 CPU가 노트를 열어 두면 61%, 가려져 있으면 87%였다. 시험은 모두 통과한 상태였다. |
| 원인 추적 | 잴 때 쓴 것은 `mac/scripts/perf.sh`다. 다른 번들 ID로 시험용 사본을 빌드해 할 일 150개, 일정 60개, 완료 기록 2,000줄, 메모 80개를 넣고, `perf-probe.swift`로 그 프로세스 하나의 CPU, 깨어나는 횟수, 메모리, 키 입력부터 반응까지의 시간을 읽는다. 하루 띠의 '지금' 선이 깜빡이는 동안 노트 전체가 매 프레임 다시 그려지고 있었다. 같은 측정에서 입력 줄이 글자마다 같은 규칙을 수십 번 새로 만드는 것, 완료 기록을 읽을 때 날짜마다 날짜 읽는 도구를 두 개씩 새로 만드는 것도 나왔다. |
| 대안 | 깜빡임을 없앤다. 다시 그리는 주기를 낮춘다. 깜빡임만 노트와 따로 그린다. |
| 선택과 이유 | 1.39에서는 깜빡임만 Core Animation에 넘겼다. 화면 모양을 바꾸지 않고 비용만 없앨 수 있었다. 깜빡임 자체는 1.40에서 하루 띠를 새로 그릴 때 없앴다. |
| 결과 | 쉴 때 CPU 61% → 0.7%, 가려졌을 때 87% → 0.3%. 입력 줄 글자 하나 0.46초 → 0.01초, 검색 열기 2.0초 → 0.2초, 켜서 노트가 보일 때까지 2.7초 → 1.0초, 10분 쓴 뒤 메모리 213MB → 136MB. |
| 그 뒤 | `perf.sh`는 저장소에 남겨 같은 데이터로 언제든 다시 잴 수 있다. 1.40의 새 하루 띠에서는 '지금' 눈금이 깜빡이지 않고, 분이 바뀔 때와 내용이 바뀔 때만 다시 그린다. 같은 종류의 문제가 Windows에도 있었다(3번). |

## 2. 집중 카드의 ×를 누르면 앱이 멈춤 (Mac 1.40.0 → 1.40.1)

| 순서 | 내용 |
| --- | --- |
| 상황 | 1.40.0을 쓰다가 내가 찾았다. 집중을 한 번 하고 나서 집중 카드의 ×(집중 그만두기)를 누르자 앱 전체가 클릭을 받지 않았다. 화면에는 새 창이 보이지 않았다. 겪은 그대로 Claude Code에 알리고 함께 원인을 찾았다. |
| 원인 추적 | 실행 중인 프로세스를 샘플링하고 그 앱의 창 목록을 보니, "그만둘까요?" 확인 쪽지(`SlipAlert`)가 크기 0×0인 모달 창으로 떠 있었다. 다른 창의 SwiftUI 버튼 동작 안에서 쪽지를 띄우면 `NSHostingView`가 아직 크기를 재지 못해 `fittingSize`가 0×0을 돌려준다. 보이지 않는 모달 창이 모든 클릭을 막고 있었다. |
| 대안 | 확인을 묻지 않고 바로 닫는다. 확인 쪽지를 누른 동작이 끝난 뒤에 띄운다. 크기를 재지 못하면 임시 크기로 먼저 그린다. |
| 선택과 이유 | 셋 다 썼다. 쪽지는 누른 동작이 끝난 뒤 뜨고, 크기가 2pt보다 작게 나오면 520 × 420으로 먼저 그린 뒤 실제 크기에 맞춘다(`PaperSlip.swift`). 쪽지를 띄우는 공통 코드를 고쳤기 때문에 다른 확인 쪽지도 같이 안전해졌다. 집중 시간이나 쉬는 시간이 끝난 뒤에는 물을 것이 없어서 ×가 묻지 않고 닫힌다(기록은 남는다). 도중에 그만둘 때는 여전히 묻는다. |
| 결과 | 확인 쪽지가 항상 보이고, ×를 눌러도 앱이 멈추지 않는다. 같은 판에서 Windows 1.25.1에도 '시간이 다 된 뒤 ×는 바로 닫기'를 똑같이 넣었다. 역시 쓰다가 본 문제 하나도 1.40.1에서 고쳤다. 30분으로 정한 할 일을 14:01에 집중하면 29분으로 시작하던 것으로, 이제 시작 시간에서 5분 안이면 정한 시간 전체로 시작한다. |
| 그 뒤 | 원인과 버전을 `PaperSlip.swift`의 `show` 함수 주석에 남겼다. 화면 스냅숏이 약 1,500장 있었지만, 이 문제는 다른 창의 버튼 동작 안에서 쪽지를 띄울 때만 생겨서 실제 앱에서 버튼을 눌러야 드러났다. |

## 3. Windows 앱이 쉴 때 CPU 5.7%, 알람 뒤 9.2% (Windows 1.23 → 1.24.0)

| 순서 | 내용 |
| --- | --- |
| 상황 | 1.24를 준비하며 Windows 앱도 Mac과 같은 데이터로 쟀다. 노트를 띄워 두고 쉴 때 CPU 5.7%, 알람이 한 번 울린 뒤에는 9.2%였다. 10분 쓴 뒤 메모리는 692MB. |
| 원인 추적 | `windows/tools/perf.mjs`가 `--demo`로 띄운 앱을 DevTools 프로토콜(렌더러)과 Node 인스펙터(main)로 잰다. 하루 띠의 '지금' 점이 쉬지 않고 깜빡이며 매 프레임 그려졌고, 숨긴 펫 창에서도 숨쉬기 애니메이션이 돌았다. 알람이 울린 뒤에는 숨겨 둔 쪽지의 물결과 흔들림이 계속 움직였다. 앱 상태를 모든 창에 보냈고, 공유 폴더를 확인할 때마다 파일을 통째로 읽었다(쉬는 동안 분당 10번). |
| 대안과 선택 | 숨긴 펫 창은 숨긴 채 두지 않고 닫았다. '지금' 점은 그릴 때 두 번만 깜빡인다. 앱 상태는 그 상태를 듣는 창에만 보내고, 메모를 적는 동안은 손이 멈출 때 한 번 보낸다. 공유 폴더는 파일 크기와 수정 시각을 먼저 보고 바뀐 파일만 읽는다. 바뀌지 않은 줄, 띠, 탭은 다시 그리지 않는다. 동작은 바꾸지 않았다. |
| 결과 | 쉴 때 CPU 5.7% → 1.5%, 알람 뒤 9.2% → 0.5%, 10분 뒤 메모리 692MB → 457MB, 쉬는 동안 파일 통째 읽기 분당 10번 → 0번, 앞으로 탭 전환 86ms → 53ms. |
| 그 뒤 | 1.25의 새 하루 띠는 분이 바뀔 때와 내용이 바뀔 때만 다시 그린다. 같은 날 1.24와 비교해 쉴 때 CPU 1.17% → 0.22%. 펫이 화면에 나와 있을 때의 CPU(약 4–7%)는 줄이지 못했다. 이 숫자는 모두 macOS 위의 Electron에서 잰 값이고, 실제 Windows PC에서는 재지 않았다. |

## 4. 하루 일정표 블록이 떨림 (Mac 1.40 → 1.41.0, Windows 1.25 → 1.26.0)

| 순서 | 내용 |
| --- | --- |
| 상황 | 하루 일정표를 쓰다가 내가 찾았다. 블록을 끌면 매끄럽지 않고 떨렸다. Mac에서는 블록을 아래로 계속 끌어도 원래 자리와 한 칸(15분, 12.5pt) 아래를 오갔고, 포인터와 최대 51.5pt 어긋났다. Windows는 떨지는 않았지만 가만히 있다가 12.5px씩 툭 뛰었고, 216프레임 중 포인터와 1px 안에 있던 건 38프레임이었다. 시험은 모두 통과한 상태였다. |
| 원인 추적 | Mac 1.40은 `DragGesture`를 블록 자신에 붙였고 좌표 공간이 기본값 `.local`이었다. 블록을 `.offset`으로 한 칸 옮기면 기준도 한 칸 옮겨 가서, 다음 이벤트의 이동량은 "포인터 이동 − 블록이 이미 옮긴 거리"가 된다. 그 값을 다시 15분 단위로 맞추면 방금 옮긴 칸이 취소된다. 같은 포인터 경로(118틱)를 옛 계산에 넣어 보니 블록 위치가 114번 바뀌고 그중 61번이 포인터와 반대 방향이었다(`mac/scripts/drag-sim-1.40.py`). 끄는 상태를 일정표의 `@State`에 둬서 한 칸마다 일정표 전체를 다시 그리고 있었다. Windows는 포인터를 화면 좌표로 바르게 쟀지만, `pointermove`마다 15분에 맞춘 자리를 블록의 `top`에 바로 썼다. 같이 보니 끄는 중 스크롤하면 블록이 어긋나고, 놓은 지점이 아니라 마지막 `pointermove` 지점에 놓이고, 할 일의 끝이 04:00이 되면 저장이 조용히 거절되는데도 '옮겼어요'가 떴다. |
| 대안 | 15분에 맞추는 계산만 고친다. 끄는 동안에는 맞추지 않고 블록이 포인터를 그대로 따라가게 하고, 맞추는 건 놓을 때만 한다. 같이 넣은 늘리기에서는, 시작만 있는 할 일(30분으로 그려짐)을 늘릴 때 시작만 있는 채로 둘지 보이던 끝을 정식 끝으로 줄지. |
| 선택과 이유 | 두 번째를 두 앱에 똑같이 넣었다. 계산만 고치면 Mac에서는 움직이는 블록을 기준으로 재는 되먹임이, Windows에서는 칸 단위로 뛰는 움직임이 그대로 남는다. 포인터는 일정표 기준(화면 좌표 + 스크롤 양)으로 재고, 맞춰질 자리는 점선과 시간 표시로 따로 보여 주고, 데이터는 놓을 때 한 번만 쓴다. Mac은 끄는 상태를 끌리는 블록과 점선만 읽는 `@Observable` 객체로 옮겨 다른 블록을 다시 그리지 않게 했고, 끄는 동안 블록의 칸과 폭도 고정했다. 시작만 있는 할 일은 늘리면 보이던 끝을 정식 끝으로 받는다. 블록이 튀지 않게 하려고서다. 규칙은 두 앱이 같은 사례(R1–R8, W3)로 확인한다. |
| 결과 | 끄는 동안 포인터와의 최대 차이: Mac 옮기기 118틱 0.20pt, 위 · 아래 끝 늘리기 0.00pt. Windows 옮기기 225프레임, 위 끝 75프레임, 아래 끝 180프레임 모두 0px. 반대로 튄 횟수 0. 끄는 동안 다시 그린 것은 시작할 때 일정표 한 번과 끌리는 블록뿐. 자동 스크롤하는 동안에도(Mac 236.7pt, Windows 271px) 블록이 포인터를 따라갔다. 가만히 둘 때 CPU는 이전과 같은 수준. |
| 그 뒤 | 측정 도구를 저장소에 남겼다. Mac은 테스트용 사본에 보낸 가짜 마우스 이벤트가 `DragGesture`까지 가지 않아서, 디버그 빌드에만 있는 재생 장치(`TimetableReplay.swift`)가 제스처와 같은 함수를 초당 60번 부르고 `mac/scripts/drag-check.sh`가 틱마다 판정한다. Windows는 `windows/tools/drag-probe.mjs`가 CDP로 실제 마우스 이벤트를 1px씩 보내고 프레임마다 블록 위치를 기록한다. 연속 입력은 움직이는 대상이 아니라 고정된 컨테이너 기준으로 재고, 화면 위치와 저장 값을 나눈다는 규칙을 [수정 기록](../docs/postmortem-timetable-drag.md)에 적었다. Mac의 실제 트랙패드 끌기와 커서 모양, Windows PC와 터치 · 펜 입력은 아직 확인하지 못했다. |
